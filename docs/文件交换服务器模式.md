## 文件交换服务器模式（exchange）

> MsgFerry 在「更严格的隔离网络」下的部署形态：不使用共享目录，而是通过一台**文件交换服务器**（file_transfer / file_rsync 等自定义同步命令）完成内网与外网之间的文件摆渡。该模式由 PR #54 实现，本文基于 issue #53 的完整讨论整理。

## 一、 为什么需要交换服务器模式

### 1. 背景与动机

有的内网和外网数据交换更加严格，**根本不支持共享目录（HGFS / 挂载盘）**，但会有一台专门用于文件交换的服务器。典型同步命令如下：

```bash
# 上传目录到文件交换服务器（-pd，push dir）
file_transfer -pd /mnt/hgfs/sharedir/vm_share nfs/vm_shared

# 从文件交换服务器拉取目录到本地（-g，get）
file_transfer -g nfs/vm_shared /mnt/hgfs/sharedir/vm_share
```

这种模型的本质是：**有明确延迟的、显式触发的、整目录粒度的快照同步**，与共享目录的「近实时双向共享」完全不同。

### 2. 两种模式对比

MsgFerry 通过一个**同步模式开关**同时支持两种形态：

| 配置 | 模式 | 说明 |
|---|---|---|
| 未配置任何 `MSGFERRY_SYNC_*` 命令 | `shared`（共享目录） | 现有行为，免同步，直接读写本地目录 |
| 配置了 `MSGFERRY_SYNC_PUSH_CMD` 或 `MSGFERRY_SYNC_PULL_CMD` | `exchange`（交换服务器） | MCP 每次读写前先同步（push / pull） |

## 二、 总体框架

### 1. 架构图

![文件交换服务器模式框架图](./文件交换服务器模式/img/框架图.svg)

### 2. 参与方与职责

- **内网侧 MCP Server**：所有同步动作的发起者。负责渲染同步命令、`spawn` 执行、超时与退避重试，是全部目录读写的唯一出入口。
- **文件交换服务器**：扮演**单向信箱**。`outbound/` 供内网上传、Worker 读取；`inbound/` 供 Worker 回写、内网拉取。
- **外网侧 Worker**：直接挂载文件交换服务器（Windows 天然同步），`queue_mode=exchange` 下扫 `outbound/` 领任务、结果回写 `inbound/`。

## 三、 核心设计：单向信箱

### 1. 单向信箱目录设计

交换模式下，内网本地目录与文件交换服务器被拆成**两个单向信箱**，杜绝整目录互相覆盖与污染：

```
内网本地 hgfs_root/            文件交换服务器 vm_shared/（Worker 直接读写）
├─ outbound/                   ├─ outbound/
│  ├─ task_<id>.json           │  ├─ task_<id>.json        ← 内网 -pd 单文件上传
│  ├─ cancel_<id>.marker       │  ├─ cancel_<id>.marker
│  └─ sent/                    ├─ inbound/
│     └─ task_<id>.json(留痕)  │  ├─ result_<id>.json      ← Worker 写
├─ inbound/                    │  ├─ <id>.stdout           ← Worker 写（大输出随结果）
│  ├─ result_<id>.json(镜像)   │  ├─ heartbeat.json        ← Worker 写
│  └─ ...(整目录 -g 拉回)      └─ processing/ lock/...     ← Worker 本地中间态，内网永不拉
```

- **`outbound/`**：内网只写、Worker 只读（上传方向）。内网写 `task_<id>.json` / `cancel_<id>.marker` → 单文件 `-pd` 上传。
- **`inbound/`**：Worker 只写、内网只读（拉取方向）。Worker 写 `result_<id>.json` / `<id>.stdout` / `heartbeat.json` → 内网整目录 `-g` 拉回。
- **`outbound/sent/`**：内网 push 成功后单文件移入留痕，位于同步范围之外，绝无二次上行。

### 2. 约定

- 内网本地 `inbound/` 只做镜像，**禁止本地往里写任何文件**——因为 `-g` 是整目录覆盖，本地 `inbound/` 每次都被远程快照整个替换，若混入本地文件会被冲掉。
- Worker 的锁文件、`processing/` 中间态、日志一律不进 `inbound/`，天然隔离，内网从不拉它们。

## 四、 同步命令配置（模板语法）

同步命令完全由用户定义，MCP 只做**占位符替换 + spawn + 超时 + 退避重试**。

### 1. 环境变量

| 环境变量 | 说明 |
|---|---|
| `MSGFERRY_SYNC_PUSH_CMD` | push 模板命令，必须含 `{src}`（本地任务文件相对路径，如 `outbound/<id>.json`）与 `{dst}`（服务器 outbound/ 相对目录）占位符，目录前缀由模板承担；本地侧前缀可用 `{hgfs_root}` 引用 `MSGFERRY_HGFS_ROOT` 展开后的绝对路径 |
| `MSGFERRY_SYNC_PULL_CMD` | pull 命令，整目录拉回；本地侧目标目录可用 `{hgfs_root}` 引用内网本地根（`{src}` / `{dst}` 不参与替换） |
| `MSGFERRY_SYNC_TIMEOUT_MS` | 单次同步命令超时（默认 30000） |
| `MSGFERRY_SYNC_RETRIES` | 同步失败退避重试次数（默认 3，退避 1s / 2s / 4s） |

> 任一 push / pull 命令被配置即进入 `exchange` 模式；两条都未配置则保持 `shared` 模式，全部同步调用短路。

### 2. 模板命令示例

模板前缀方案下，**服务器侧目录前缀（如 `nfs/vm_share/`）完全由用户在同步命令模板里写**，`{src}` / `{dst}` 只替换成相对路径；**本地侧前缀建议用 `{hgfs_root}` 占位符**——它会在渲染时展开为 `MSGFERRY_HGFS_ROOT` 的值（含 `$HOME` 展开后的绝对路径），这样本地根目录只声明一次，改 `MSGFERRY_HGFS_ROOT` 时同步命令自动跟随，无需重复写 `vm_share/`：

```bash
# 上传方向：单文件上传到服务器 outbound/
#   {src} → outbound/<id>.json（相对），{hgfs_root} → /root/.msgferry/vm_share（展开后），{dst} → outbound/
MSGFERRY_SYNC_PUSH_CMD='file_transfer -pd {hgfs_root}/{src} nfs/vm_share/{dst}'
# 或自定义同步工具（file_rsync 同样适用）
MSGFERRY_SYNC_PUSH_CMD='file_rsync -av {hgfs_root}/{src} nfs/vm_share/{dst}'

# 拉取方向：整目录拉回服务器 inbound/ 到本地镜像（{hgfs_root} → 内网本地根，源带前缀）
MSGFERRY_SYNC_PULL_CMD='file_transfer -g nfs/vm_share/inbound {hgfs_root}/inbound'
```

> 若你的本地镜像目录名恰好不是 `hgfs_root` 的 basename（例如本地根是 `~/.msgferry/data`，而交换服务器前缀是 `vm_share`），也可以继续沿用旧写法，直接用绝对路径或 `$HOME` 写法写本地侧路径，`{hgfs_root}` 与绝对路径可混用。

### 3. 模板语法规则

- 占位符替换用纯字符串 `replaceAll`，**不做 shell 解析**；
- push 命令里 `{src}` 在每次 push 前替换为**本地任务文件相对路径** `outbound/<task_id>.json`（目录前缀如 `{hgfs_root}/` 或 `vm_share/` 由模板承担）；
- push 命令里 `{dst}` 统一替换为**服务器 outbound/ 目录**（相对目录 `outbound/`，前缀 `nfs/vm_share/` 由模板承担，MCP 不校验）；
- push / pull 命令里 `{hgfs_root}` 均替换为**配置的 `MSGFERRY_HGFS_ROOT`（含 `$HOME` 展开后的绝对路径）**，避免本地根目录重复声明；
- pull 命令是静态命令，`{src}` / `{dst}` 不参与替换，仅 `{hgfs_root}` 生效；
- 用户命令里可带任意自定义参数 / 自定义同步工具；
- 非零退出码 = push / pull 失败；退避重试 3 次仍失败则抛 `sync_failed`。

### 4. 推荐参数

- `MSGFERRY_MAX_WAIT_MS`：交换模式下建议调到 **120000**（覆盖「上传 → worker 执行 → 拉回」一整轮，秒级同步下足够）。
- Worker 配置 `result_ttl_sec`：交换模式建议调大到 **3600**，避免结果没被拉回就被 GC 清掉。

## 五、 任务执行流程

### 1. 任务执行时序图

![任务执行时序图](./文件交换服务器模式/img/任务执行时序图.svg)

### 2. submit_ssh_task（同步阻塞直至超时）

```
Claude 调 submit_ssh_task(cmd)
  └─ MCP: syncPull（-g 拉回心跳，判定 worker 在线）
       → 写 outbound/task_<id>.json
       → syncPush（单文件 -pd 上传）
       → 阻塞循环 { syncPull（-g 拉回 inbound/）→ 查 result_<id>.json → 超时检查 → sleep }
外网 Worker: 轮询 outbound/ → 领取任务 → SSH 执行 → 结果写 inbound/result_<id>.json
内网侧: 循环拉到结果即返回；超时写 cancel marker 并 push，只返回 timeout
```

- 交换模式下阻塞时长 = 同步往返 × 2 ~ 3 + 命令执行时间（秒级同步下可接受）；
- 超时后**不再误标 cancelled**，只返回 `timeout`，任务仍在 worker 侧执行，可用 `query_task_status` 续捞；
- push 失败返回 `sync_failed`；pull 失败**不算 Worker 离线**，重试到 `max_wait_ms` 封顶。

### 3. query_task_status（先拉再查）

```
Claude 调 query_task_status(task_id)
  └─ MCP: syncPull → 查本地 inbound/result_<id>.json
       → 命中返回结果
       → 未命中但任务在 outbound/+sent/ → pending
       → 都找不到 → pending（不误报 not_found / Cancelled）
```

### 4. cancel_task（尽力而为）

```
Claude 调 cancel_task(task_id)
  └─ MCP: syncPull（确认任务状态）
       → 写 outbound/cancel_<id>.marker
       → syncPush（单文件上传）
Worker: 下一轮看到 cancel marker → 中止该任务 → 回写 inbound/result_<id>.result
```

取消标记要等下一轮 push 才到 worker，worker 可能已执行完——语义降级为「尽力取消」。

### 5. check_bridge_health（放宽心跳）

```
Claude 调 check_bridge_health
  └─ MCP: syncPull（-g 拉回 inbound/，含心跳）
       → 判定 = 文件服务器可达 && 心跳存在 && shutdown_at==null → online
```

交换模式**放弃 last_beat 15s 实时判定**（同步周期内必然超时），Worker 刚挂在内网侧有最长一个同步周期的感知延迟。

## 六、 Worker 侧配合

外网 Windows 直接挂载文件交换服务器（天然同步），Worker 只需配置 `queue_mode: exchange`：

```yaml
# <hgfs_root>/config/worker.yaml
queue_mode: exchange      # shared（默认）| exchange
executor: mock            # 或 ssh2
result_ttl_sec: 3600      # 交换模式建议调大，保结果不被 GC 提前清掉
```

交换模式下 Worker：

1. 主循环扫 **`outbound/`**（而非 `pending/`）领取任务，过滤 `.tmp` 与取消标记；
2. 结果回写 **`inbound/result_<id>.json`**（大输出随批次写 `inbound/<id>.stdout`，不写 `outputs/`）；
3. 心跳额外落一份 **`inbound/heartbeat.json`**（与结果合并成同一次 `-g` 拉回）；
4. 取消检查改为查 `outbound/cancel_<id>.marker`，消费后清理该任务的 cancel marker（防残留被下次整目录拉回再看到）；
5. GC 扫 `inbound/`（心跳文件不参与 GC）。

## 七、 实际应用：MCP 侧与 Worker 侧配置

> 本节是 exchange 模式的**落地配置清单**，回答两个最直接的问题：内网 MCP 侧怎么配置 exchange 模式、外网 Worker 侧怎么启动。两侧配置相互独立、各配各的，唯一对齐点是「内网 push 的 `{dst}` 与 Worker 挂载的 `--hgfs-root` 指向文件交换服务器上的同一个 `outbound/` 目录」。

### 1. 配置总览：两侧各配什么

| 角色 | 运行侧 | 配置方式 | 关键点 |
|---|---|---|---|
| **MCP Server** | 内网 Linux | 全部由**环境变量**注入（`.mcp.json` 的 `env`，见 §7.2） | 配置 `MSGFERRY_SYNC_PUSH_CMD` / `MSGFERRY_SYNC_PULL_CMD` 即进入 exchange；`MSGFERRY_HGFS_ROOT` 填**内网本地镜像目录** |
| **Node Worker** | 外网 Windows | 命令行 `--hgfs-root` + 配置文件 `<hgfs_root>/config/worker.yaml` | `queue_mode: exchange` 开启交换；`--hgfs-root` 填**文件交换服务器挂载目录**（Worker 直接读写） |

- 两侧**不再共用同一个本地目录**：内网本地目录与文件交换服务器目录物理分离，靠 push / pull 同步（见第三章单向信箱）。
- Worker 不配置任何同步命令，它直接挂载文件交换服务器，天然同步。

### 2. MCP 侧配置（内网 Linux，`.mcp.json` 环境变量）

MCP Server 全部配置由环境变量注入，exchange 模式只需在 `.mcp.json` 的 `env` 里追加 4 个 `MSGFERRY_SYNC_*` 变量，其余保持 shared 模式一致。仓库 `packages/mcp-server/.mcp.json` 已内置完整示例：

```json
{
  "mcpServers": {
    "msgferry-bridge-exchange": {
      "command": "node",
      "args": ["./index.mjs"],
      "env": {
        "MSGFERRY_HGFS_ROOT": "$HOME/.msgferry/vm_share",
        "MSGFERRY_MAX_WAIT_MS": "120000",
        "MSGFERRY_POLLING_INITIAL": "500",
        "MSGFERRY_POLLING_MAX": "3000",
        "MSGFERRY_SYNC_PUSH_CMD": "file_transfer -pd {hgfs_root}/{src} nfs/vm_share/{dst}",
        "MSGFERRY_SYNC_PULL_CMD": "file_transfer -g nfs/vm_share/inbound {hgfs_root}/inbound",
        "MSGFERRY_SYNC_TIMEOUT_MS": "30000",
        "MSGFERRY_SYNC_RETRIES": "3",
        "LOG_SAVE": "1"
      }
    }
  }
}
```

关键字段说明：

- `MSGFERRY_HGFS_ROOT`：填**内网本地镜像目录**（如 `$HOME/.msgferry/vm_share`，MCP 启动时用 `os.homedir()` 自动展开为家目录绝对路径，也支持 `~/.msgferry/vm_share` 写法；**目录不存在时启动会自动 `mkdir` 创建**），不再是共享挂载点，而是内网这一侧的 `outbound/` / `inbound/` 工作目录；
- `MSGFERRY_SYNC_PUSH_CMD`：**必填**。上传方向模板命令，必须含 `{src}`（替换为本地任务文件相对路径 `outbound/<id>.json`）与 `{dst}`（替换为服务器 `outbound/` 相对目录）两个占位符；**本地侧前缀用 `{hgfs_root}` 占位符引用 `MSGFERRY_HGFS_ROOT`（自动展开为内网本地根绝对路径），服务器侧前缀（如 `nfs/vm_share/`）由模板承担**，这样本地根目录只声明一次，换目录只改 `MSGFERRY_HGFS_ROOT` 一行即可；
- `MSGFERRY_SYNC_PULL_CMD`：**必填**。拉取方向命令，整目录把服务器 `inbound/` 拉回本地镜像，本地侧目标目录用 `{hgfs_root}/inbound` 引用内网本地根（`{src}` / `{dst}` 不参与替换，仅 `{hgfs_root}` 生效）；
- `MSGFERRY_SYNC_TIMEOUT_MS`：单次同步命令超时（默认 `30000`）；
- `MSGFERRY_SYNC_RETRIES`：同步失败退避重试次数（默认 `3`，退避 1s / 2s / 4s）；
- `MSGFERRY_MAX_WAIT_MS`：exchange 模式建议 **120000**，覆盖「上传 → worker 执行 → 拉回」一整轮；
- 以上任一条同步命令被配置即自动进入 `exchange` 模式；两条都不配则保持 `shared` 模式，同步全部短路。

### 3. Worker 侧启动（外网 Windows）

Worker 侧**不需要配置任何同步命令**，它直接挂载文件交换服务器（天然同步）。启动只需两件事：

**① 配置文件** `<文件交换服务器挂载目录>/config/worker.yaml` 里开启 exchange：

```yaml
# 文件交换服务器挂载目录下 config/worker.yaml（Worker 视角 Windows 路径）
queue_mode: exchange   # shared（默认）| exchange
result_ttl_sec: 3600   # 交换模式建议调大，保结果不被 GC 提前清掉
```

**② 命令行启动**（其余参数全部从 `config/worker.yaml` 读取）：

```bat
:: ssh2 真实执行（SSH 信息从 config/worker.yaml 读取）
msgferry-worker --hgfs-root Y:\nfs\vm_share

:: 需要业务日志落盘时，追加日志两个命令行参数
msgferry-worker --hgfs-root Y:\nfs\vm_share --log-save 1 --log-dir logs\worker
```

关键点：

- `--hgfs-root` 填**文件交换服务器在 Windows 侧的挂载目录**（如上例 `Y:\nfs\vm_share`，即文件交换服务器根 `nfs/vm_share` 挂载到 `Y:` 盘后的目录），Worker 在 exchange 模式下扫 `outbound/` 领任务、结果写 `inbound/`；
- 队列模式由配置文件 `queue_mode: exchange` 决定，**不通过命令行传**；
- 日志两个字段（`--log-save` / `--log-dir`）走命令行，其余（SSH、策略、轮询、心跳、结果保留期）走配置文件；
- `result_ttl_sec` 建议 3600：内网拉回周期较长，避免结果还没拉回就被 GC 清掉。

### 4. 两侧对齐检查表（部署前自检）

| 检查项 | MCP 侧（内网） | Worker 侧（外网） | 是否一致 |
|---|---|---|---|
| 服务器 `outbound/` | `MSGFERRY_SYNC_PUSH_CMD` 的 `{dst}` 指向它 | `--hgfs-root` 下的 `outbound/` | ✅ 必须同一目录 |
| 服务器 `inbound/` | `MSGFERRY_SYNC_PULL_CMD` 的源指向它 | `--hgfs-root` 下的 `inbound/` | ✅ 必须同一目录 |
| 队列模式 | `MSGFERRY_SYNC_*` 已配置 → exchange | `queue_mode: exchange` | ✅ 两侧都开启 |
| 结果保留期 | `MSGFERRY_MAX_WAIT_MS` ≥ 120000 | `result_ttl_sec` ≥ 3600 | ✅ 建议按此对齐 |

> 常见踩坑：Worker 的 `--hgfs-root` 若误填成**内网本地镜像目录**，会让 Worker 扫不到内网 push 上去的 `outbound/`，导致任务永远 pending。务必让 Worker 指向**文件交换服务器挂载目录**，而不是内网 `MSGFERRY_HGFS_ROOT` 那个目录。

## 八、 两种模式对照速览

| 环节 | shared（现状） | exchange（PR #54） |
|---|---|---|
| 提交 | 写 `pending/<id>.json` | 写 `outbound/<id>.json` → push 单文件 → 归档 `sent/` |
| 结果 | 直接读 `completed / failed/` | 每轮 pull 整目录 `inbound/` → 本地镜像匹配 |
| 心跳 | `last_beat` 15s 实时判定 | 可达 + 存在 + 未 shutdown（放宽） |
| 超时 | 写 cancelled 标记（误标风险） | 只返回 timeout，写 cancel marker 尽力取消，可 query 续捞 |
| 取消 | 实时生效 | 尽力而为（等下一轮 push） |
| 大输出 | `outputs/<id>.stdout` | `inbound/<id>.stdout` 随结果批次拉回 |
| 同步命令 | 无 | `MSGFERRY_SYNC_PUSH_CMD`（模板 `{src}` / `{dst}` / `{hgfs_root}`）+ `MSGFERRY_SYNC_PULL_CMD`（静态，支持 `{hgfs_root}`） |

## 九、 测试（无真实交换服务器时用 cp 模拟）

当前没有可用于测试的文件交换服务器，仓库提供 `scripts/sync-mock.mjs` 用 **cp 命令模拟 file_transfer**，并完全按“模板前缀”方案模拟真实目录情况：

```bash
# 1. 启动 Worker（exchange 模式，worker 挂载根为 test/temp_server/nfs/vm_share）
```

exchange 模式的测试目录与真实路径对应：

| 测试路径 | 真实环境对应 | 谁在使用 |
|---|---|---|
| `test/temp` | 内网本地根 `~/.msgferry/vm_share` | MCP Server（内网） |
| `test/temp_server` | 文件交换服务器根 | sync-mock（MSGFERRY_SYNC_MOCK_SERVER） |
| `test/temp_server/nfs/vm_share` | Worker 挂载 `Y:\nfs\vm_share` | Worker（--hgfs-root） |

`sync-mock.mjs` 语义与 `file_transfer` 对齐（默认 `MSGFERRY_SYNC_PUSH_CMD` 已改用 `{hgfs_root}` 占位符，本地侧自动展开为内网本地根绝对路径）：

- `-pd {hgfs_root}/{src} nfs/vm_share/{dst}`：单文件上传，`{hgfs_root}` 展开为内网本地根 `test/temp` 的绝对路径、`{src}` 为相对 `outbound/<id>.json`，拼接后是绝对源文件路径；dst 带前缀 `nfs/vm_share/` 相对服务器根 `test/temp_server` 解析，落点 `test/temp_server/nfs/vm_share/outbound/`；
- `-g nfs/vm_share/inbound {hgfs_root}/inbound`：整目录拉回并完全替换本地目录，源带前缀相对服务器根解析，本地目标用 `{hgfs_root}` 展开为内网本地根；
- 服务器根由环境变量 `MSGFERRY_SYNC_MOCK_SERVER` 指定（默认 `test/temp_server`）；
- 内网本地根由 `MSGFERRY_SYNC_MOCK_LOCAL` 指定（默认内网 `test/temp`）；兼容旧相对前缀写法时，模板 src 前缀由 `MSGFERRY_SYNC_MOCK_LOCAL_PREFIX` 指定（默认 `vm_share/`），改用 `{hgfs_root}` 后 src 为绝对路径，该前缀不再生效；
- `MSGFERRY_SYNC_MOCK_DELAY_MS`：模拟同步延时（默认 1000ms），设为 `0` 可完全关闭延时，便于对比测试。

在真实 `file_transfer` 环境下，只需把 `MSGFERRY_SYNC_PUSH_CMD` / `MSGFERRY_SYNC_PULL_CMD` 替换为真实命令，其余代码零改动。

## 十、 必须接受的三个代价

1. **阻塞时长不可控**：`submit` 单次调用 = 同步往返 × 2 ~ 3 + 命令执行时间，比共享目录模式明显变长。
2. **取消是尽力而为**：cancel marker 要等下一轮 push 才到 worker。
3. **心跳判定放宽**：不按 last_beat 15s 实时判离线，Worker 刚挂最长一个同步周期才能感知。

这三个代价在共享目录模式下完全不存在（维持现状），只有配置了同步命令才生效。
